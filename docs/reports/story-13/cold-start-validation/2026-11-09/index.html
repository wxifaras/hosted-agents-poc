Summary

  • We tested real deployed Hosted Agents in Microsoft Foundry, not a local simulation.
  • The median first useful response was 6.39 seconds without snapshots and 1.46 seconds with snapshots: 77.1% less waiting.
  • The agent application's preparation time was 4.264 seconds without snapshots and 0.135 seconds with snapshots.
  • Adding precompiled Python recorded 1.36 seconds, compared with 1.46 seconds for snapshots alone. This small sample does not prove a repeatable extra gain.
  • 63 of 63 planned cloud checks passed. 11 earlier failed diagnostic attempts are disclosed separately, not counted as successful comparisons.

Cold start means the first request in a new session. Warm means the agent is already running. A median is the middle measured result, not a worst-case promise.

What we tested

Architecture. One isolated Python Responses agent ran in a container hosted by Microsoft Foundry, with CPU 0.5 and memory 1Gi. Separate deployed versions represented the configurations below. No AI model, external tools, or multi-agent workflow was included, so the test isolates hosted startup.

SDK. We used snapshot-capable Agent Server Core 2.3.0 and Responses 2.4.0. SDK versions and compute stayed the same across conditions; the baseline and snapshot-only versions also used the same container image.

Features and techniques compared:

  • Baseline: normal container startup, with memory snapshots disabled.
  • Native memory snapshots: Foundry's enableMemorySnapshot setting restores initialized application state. SDK before-snapshot and after-restore hooks verified capture and restoration.
  • Snapshots plus precompiled Python: the optimized image additionally compiled Python application, dependency, and standard-library bytecode during the image build, not at startup.

All images used a slim multistage build, build-time dependency installation, and disabled user-site packages (PYTHONNOUSERSITE=1). We measured real cold starts, warm session reuse, and resume after idle using Foundry's native latency diagnostics; no artificial startup delays were added.

How did we measure response times?

Think of a stopwatch on the computer sending the request. We measured how long it took the real hosted agent to send back its small, useful reply.

  1. Start the clock before the request. The test runner started a precise timer immediately before asking the hosted agent to respond. For a cold-start request, Foundry created the new session as part of that request; we did not create it separately beforehand and accidentally warm it up.
  2. Stop when the complete reply has arrived. The main response-time number includes the request trip, any startup work, the agent's small reply, and the trip back. It stops after the response body is received, before local parsing and checks. It is not just the time to receive headers or the first network bytes, and it is not AI-model time to the first token.
  3. Check what kind of start actually happened. Foundry's own diagnostics had to confirm cold, warm, or resumed execution. The runner also checked the returned session, version, reply, and synthetic state. A new session alone was not enough to call a result a confirmed cold start. Failed or unconfirmed attempts were not treated as successful comparison samples, and requests were not automatically retried.
  4. Record application preparation separately. Foundry also reported how long the application took to become ready inside the container. That is the preparation graph, not the whole response journey. We did not add it to the response time because the two measurements overlap. Any later read-only checks for delayed diagnostics happened outside the recorded successful response time.
  5. Repeat and compare the middle result. Each option had ten confirmed cold starts, ten warm calls, and one return after idle. The headline compares the median of the ten cold starts for each option. A median is the middle result; the detailed graphs also show the spread. The single resumed request is a continuity check, not a reliable estimate of typical resume latency.

Keep the comparison fair. The baseline and snapshot-only options used the same image, SDKs, and compute; only snapshots changed. The optimized option used a different, precompiled image. Conditions ran one after another, not as a randomized trial. There was no AI model or external tool call, so these results describe this probe's startup, not a complete customer workflow, a worst-case response time, or a service guarantee.

Conclusion

Memory snapshots were the main startup improvement in this controlled test. They are a good candidate for agents that keep required state outside the container. Validate the customer's real model and tools next, before promising end-to-end response times.

Recommended next steps

  1. Check that essential state is stored outside the agent container.
  2. Consider Foundry's native memory snapshots with a supported SDK.
  3. Repeat the measurement with the customer's actual model, tools, and workload before production.
Important state limitation. With snapshots, changes to application memory and local files do not survive idle/resume. Store required state outside the agent container. This experiment does not validate customer conversation latency, cross-user authorization, or production reliability.

Native feature and SDK findings

The existing root project pins Responses 2.2.0b1 and resolves Core 2.1.0. The isolated experiment pins Core 2.3.0, Responses 2.4.0, and Projects 2.10.0. Its own lockfile captures all transitive dependencies. Do not upgrade the root project's packages for this story.

  • Core 2.3.0 provides public before-snapshot, after-restore, and readiness hooks. Upgrade it together with Responses 2.4.0: older Responses versions reference an internal constant removed by Core.
  • Responses 2.4.0 includes protocol-scoped task activation, original-subject handling, and user-partitioned local storage/replay changes. Background recovery and steering remain disabled in this probe.
  • Core 2.3.1b1 is a newer preview with an A2A tracing fix, not a documented startup optimization. It is not required for this experiment.
  • The SDK's generated CreateResponse export is not recognized as a static type alias by mypy. The handler accepts Mapping[str, object], matching the dictionary request without casts or private SDK imports.
  • Native azd snapshot guidance requires azd >= 1.37.0 and the documented azure.ai.agents extension 1.0.0-beta.23. Check actual versions before any deployment; the root project's older declared minimum is not sufficient.

Critical behavior: a memory snapshot is the initialized version baseline, not a checkpoint of a user's ongoing session. Snapshot-enabled idle/resume currently does not preserve process changes or local files, including $HOME. Do not enable it on the existing file-dependent Data Analysis story.

Condition Image Native snapshot flag Purpose

Both image targets install dependencies at build time, use a small multistage runtime, and disable user-site loading. C adds precompiled dependency/stdlib bytecode on a best-effort basis, and strict application compilation. Thus C does not claim improvements already present in A/B.

Use the same Foundry project/region, agent name, CPU (0.5), memory (1 GiB), configuration, input shape, SDK versions, and sequential concurrency. Each cold POST creates a new native session implicitly; the isolated endpoint is pinned to one immutable version, and returned session metadata is verified. Version creation and asynchronous snapshot preparation are outside invocation timings; record preparation separately if operationally relevant.

Default comparison budget per condition: 10 new sessions, 10 first POSTs, 10 warm POSTs, and 1 resumed POST: at most 21 invocations, plus session management and at most three diagnostic GETs per invocation. Across three conditions: 30 new sessions and at most 63 invocations. There are no model tokens. Keep the machine awake during idle waits. Live runs use 210 seconds to allow native idle suspension beyond the 120-second threshold.

The configured idle timeout is 120 seconds. Sleeping is not proof of suspension: only a native resume diagnostic passes the resume check. An unexpected warm, cold, or absent classification is a recorded failure, not silently relabeled or retried. Adjust the idle wait in a separately identified run if needed.

Include x-ms-debug-latency-enabled: true. Capture native platform preprocessing, infrastructure setup, container readiness, handling/response headers, and first/last-byte timings when available. Diagnostic GETs retrieve original request timings; their duration is not added to client POST timings.

Client observations measure response headers, first body chunk, and full response completion. Implicit session creation is inside the cold POST's timed journey. A response-begin header is not time to first useful body content; first body chunk is not model time-to-first-token. Complete JSON delivery is the useful response for this non-streaming no-model workload. The cold client journey graph includes session creation and response completion in one POST; warm/resume reuse the returned session ID. Do not pre-create sessions for cold measurements: live validation showed create_session warms the container before the first POST. That moves startup cost; it does not eliminate it. The earlier explicit-create diagnostic files retain their separate session-creation timings.

Persist each attempt immediately to JSONL. Save only allowlisted native headers, response correlation IDs, version/image controls, timestamps, hashed session/ project bindings, numeric timings, and synthetic comparison outcomes. Do not save credentials, caller identity, arbitrary headers, or the synthetic markers.
