Story6: Hosted tool approval

Final results deep dive · synthetic POC · authenticated Foundry toolbox proxy

Hosted approval, rejection, discovery and owner controls worked. Direct authorized toolbox calls bypassed human approval. Evaluation complete within the tested proxy scope; universal approval enforcement is not achieved.

Contents: Final outcomes · Criterion 1 · Criterion 2 · Criterion 3 · Criterion 4 · Criterion 5 · Notifications · Ownership · Limits · Evidence and downloads

What worked and what did not

Worked through Hosted Agents

Human approve/reject, fresh-client pending discovery, original-owner continuation, conversation/file continuity and authenticated toolbox access.

Unauthorized user denied

Another real authenticated user could reach its own route but could not inspect or decide the owner's operation. The owner remained able to continue.

Direct approval gate did not work

An otherwise authorized caller executed the proxy tool without approval despite require_approval=always. This recorded check remains FAIL.

Evaluation coverage is not the same as a passing control. These are final selected observations, not a deployment/version timeline, not a combined rerun on one release, and not a production certification.

1. Approve/reject a multi-agent MCP action; identify enforcement ownership

Result: Works, scoped

What worked

Coordinator delegates context to Research, exposes the actual pending MCP request, and continues after approval or rejects without executing the tool

What did not work / why

The provider approval path is not a shared server-side gate covering every MCP caller

How this was validated

  1. Requester invokes the dedicated Hosted coordinator.
  2. Coordinator calls unchanged Research for context.
  3. Native provider returns the proposed MCP tool and arguments without dispatching the pending call.
  4. Client reviews the actual request and explicitly approves or rejects.
  5. The original bound operation completes or rejects; provider-reported calls remain separately counted.

2. Discover pending approvals, submit decisions, and assess notification options

Result: Works, with notification limitations

What worked

A fresh client discovers the pending operation through custom `inspect`; explicit decisions resume it. Polling, webhook and Event Grid options were assessed

What did not work / why

No native approval-specific webhook/Event Grid contract was established; generic completion is not approval

How this was validated

  1. A fresh client inspects the existing owner-bound operation.
  2. Coordinator reads authoritative pending state; inspection adds no model/tool execution.
  3. The explicit decision references that pending request, not a new operation.
  4. Logical operation phase, not generic response completion, determines whether review is still pending.
